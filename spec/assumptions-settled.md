# Assumptions: settled groups

Groups of assumptions whose work is built and settled, moved out of `spec/assumptions.md` to keep that file under its size limit. The rules of `spec/assumptions.md` apply here too: an item that is decided goes into `DECISIONS.md` and its topic file, and is removed.

## Phase 2 leftover screens (`spec/screens-campaign.md`)

- **A-40. Where the window learns that a run needs the licence dialog.** Only the main process knows which workflow a run gets. **Assumption:** the window sends the run as usual; the command refuses with `licence_not_confirmed` and `details.workflow` before any job row; the app store then shows the dialog and sends the run again with `licenceConfirmed: true` on Confirm, the way the key dialog works. The window holds no copy of the workflow choice. `details` may now name a workflow ID. *LD-1, S2-4 and S2-6. Change later: easy.*
- **A-41. How the panels know a workflow is `trial`.** **Assumption:** `comfy.getInfo` marks each workflow `offered` when it is the one the user's run of that job (and video start pair) gets, worked out by the same function the commands use. The panels read the mark; they hold no rule of their own. *S2-4 and S2-7. Change later: easy.*
- **A-42. The address dialog.** FR-255 asks for the address at the moment of a run. **Assumption:** a refused run opens the address dialog (save, then the run is sent again) instead of an "Open Settings" button; failed runs whose reason is about the server still offer "Open Settings". The privacy paragraph shows in the dialog as well as in Settings, from one constant. *S2-6. Change later: easy.*
- **A-43. Where a dropped file's path comes from.** A sandboxed window cannot read a dropped file's path [REQ: FR-246]. **Assumption:** the preload gives one function, `window.drop.pathOf`, which asks Electron (`webUtils.getPathForFile`) for the path of a `File` the user dropped; it gives nothing for a file the page made. A drop never imports by itself: the import dialog always opens and the user presses "Import". `asset.import` checks a dropped path exactly as a picked one, so the main process gains no new trust. This widens the renderer path rule in `spec/security.md`, so the slice gets a full security review. *S2-3. Change later: easy (remove the function).*
- **A-44. Colours and required files on the brief form.** FR-033's rule set also holds a palette and required files; the brief carries neither. **Assumption:** the form edits the word lists and offers "Copy the rules from another campaign"; colours and required files are set after the campaign is made, on the rule-set screen of Phase 6 (`ruleSet.update` exists). *S2-14. Change later: easy.*
- **A-45. After "Create campaign".** **Assumption:** the new campaign opens at once, so the slot view (FR-042, "after the brief is confirmed") is the next thing the user sees. *S2-2. Change later: easy.*
- **A-46. The slot view only shows.** **Assumption:** it lists the master's slots as filled or empty, with candidate pictures, and has no controls. Putting a candidate into a slot comes with the Phase 3 picture chooser. *S2-15. Change later: easy.*
- **A-47. What a variant tile does, and which variant the overview's panels work on.** **Assumption:** a tile is one button; tiles are reached with Tab, not arrow keys. A plain click opens the variant's tab and shows it (Q-041). The small "+" beside the tile, and Cmd-click (Ctrl-click on Windows), open the tab behind and keep the overview showing. The variant shown last in its own tab stays the one the overview's panels work on, and its tile is drawn pressed (`aria-pressed`); opening a tab behind does not change it; before any variant tab is shown, it is the first variant of the grid. A tile shows the variant's thumbnail (`spec/editor.md`, "Thumbnails on the screens"); the box in the variant's shape is shown only where no thumbnail is passed. The rule is in `spec/editor.md`, "Variant tabs". *S2-16, P3-9, P3-10. Change later: easy.*
- **A-48. The package dialog draws no folder path.** **Assumption:** the dialog reports the number of files and the size, not where the package went; the user chose the folder a moment before. No path rule changes. *S2-12. Change later: easy.*
- **A-49. Left out of the ComfyUI screen work.** **Assumption:** the run dialog of FR-256 (address and workflow shown before a ComfyUI run) is Phase 4's run confirmation dialog, built there (`spec/screens-ai.md`). The run list says nothing extra about a queued agent run that will be cancelled at its turn: the row reads "Waiting", then "Cancelled". *Phases 2 and 4. Change later: easy.*
- **A-50. A refusal inside a dialog.** Every command goes through the app store, which puts a refusal in the error banner, behind the dialog. **Assumption:** a dialog also shows the refusal inside itself; the banner keeps it too. The address and licence dialogs, when cancelled, leave the banner empty, as the key dialog does. *All new dialogs. Change later: easy.*
- **A-51. Cancelling the brief form.** **Assumption:** "Cancel" closes the form and drops what was typed, without asking. *S2-13. Change later: easy.*
- **A-52. Who writes `licenceConfirmed`.** **Assumption:** `settings.update`, which agents cannot call; no command of its own. A bad value in the settings file reads as an empty list and leaves the other settings as they are. *S2-4. Change later: easy.*
